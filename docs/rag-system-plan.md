# RAG 问答系统实施方案

## 1. 目标

构建一个可落地的 RAG（Retrieval-Augmented Generation，检索增强生成）问答系统，用于基于私有知识库进行准确问答，并具备以下能力：

- 支持文档导入、切分、向量化、索引构建
- 支持语义检索、召回重排、上下文组装
- 支持基于大模型的答案生成
- 支持引用来源返回，便于溯源
- 支持基础评测、监控和后续迭代

当前阶段目标：

- 先完成实施步骤和评审材料
- 待你审核通过后，再进入系统设计
- 设计确认后，再进入代码实现与仓库建设

## 2. 建设边界

本阶段只做方案，不做以下内容：

- 不做详细架构设计图
- 不写业务代码
- 不接入具体模型或向量库
- 不定义最终 API 协议
- 不部署到生产环境

## 3. 推荐实施步骤

### 第 1 步：明确业务场景与验收目标

先定义系统服务对象和问题范围，否则后续检索效果无法评估。

需要确认的内容：

- 知识库类型：PDF、Word、Markdown、网页、数据库记录、FAQ
- 业务场景：企业知识问答、客服问答、技术文档问答、内部制度问答
- 问答语言：中文、英文或多语言
- 目标用户：内部员工、外部客户、开发者、运营人员
- 响应要求：准确率优先、速度优先，还是两者平衡

产出物：

- 需求说明
- 数据范围说明
- 初版验收指标

### 第 2 步：梳理知识库数据

RAG 成败首先取决于数据质量。

需要执行的工作：

- 盘点已有知识源
- 区分结构化与非结构化数据
- 清理无效内容、重复内容、格式噪声
- 标记文档元数据，如标题、来源、时间、部门、权限等级
- 识别高频问题与标准答案样本

产出物：

- 数据清单
- 数据质量问题清单
- 文档元数据规范

### 第 3 步：定义文档处理与切分策略

切分策略直接影响召回效果和生成质量。

需要设计的内容：

- 文档解析方式：按格式类型分别处理
- 文本清洗规则：页眉页脚、乱码、重复段落、目录噪声
- 切分粒度：按段落、标题层级、固定 token 长度、滑窗重叠
- 元数据保留策略：章节、页码、来源链接、更新时间

建议评估维度：

- 单 chunk 是否语义完整
- chunk 是否过长导致召回噪声
- chunk 是否过短导致上下文不足

产出物：

- 文档处理规范
- chunk 切分策略说明

### 第 4 步：确定向量化与索引方案

这是检索层的核心。

需要确定的内容：

- Embedding 模型选型
- 向量维度与成本
- 向量库选型
- 是否混合检索：向量检索 + 关键词检索
- 索引更新方式：全量重建或增量更新

常见方案方向：

- 快速起步：`FAISS`
- 工程化落地：`Milvus`、`pgvector`、`Elasticsearch/OpenSearch`
- 中文问答通常建议保留 BM25 或关键词检索能力，避免纯向量检索遗漏精确术语

产出物：

- 向量化方案
- 索引方案
- 更新策略说明

### 第 5 步：设计检索链路

基础 RAG 不应只有“向量检索 + 直接生成”。

建议链路：

1. 用户问题预处理
2. 查询改写或问题标准化
3. 初步召回
4. 元数据过滤
5. 重排 rerank
6. 上下文拼接
7. 调用大模型生成答案
8. 返回答案与引用片段

可选增强能力：

- Multi-query 检索
- HyDE
- Query rewrite
- Parent-child retrieval
- Self-RAG / corrective retrieval

产出物：

- 检索流程说明
- 上下文组装规则
- 答案引用规则

### 第 6 步：设计问答生成策略

生成层的目标不是“写得像”，而是“基于证据回答”。

需要定义的内容：

- System Prompt 约束
- 是否必须基于检索结果回答
- 无答案时的兜底策略
- 是否返回引用来源
- 是否返回置信度或命中依据
- 是否支持追问和多轮对话

建议原则：

- 没有证据时明确说明“不确定”或“知识库未命中”
- 禁止模型脱离知识库自由发挥
- 优先输出结构化答案，便于前端展示

产出物：

- 生成策略说明
- Prompt 规范
- 无答案与低置信兜底规则

### 第 7 步：定义评测体系

没有评测，RAG 很容易停留在“看起来能用”。

建议建立三类评测：

- 检索评测：Recall@K、MRR、Hit Rate
- 生成评测：答案正确性、引用一致性、完整性
- 系统评测：响应时间、吞吐、成本

建议准备：

- 一批标准问答集
- 一批困难问题集
- 一批无答案问题集

产出物：

- 评测数据集
- 评测指标定义
- 基线结果记录

### 第 8 步：设计系统接口与模块边界

在实现前要先划清模块职责。

建议的核心模块：

- `ingestion`：文档导入
- `preprocess`：清洗与切分
- `embedding`：向量化
- `indexing`：索引构建
- `retrieval`：检索与重排
- `generation`：答案生成
- `evaluation`：评测
- `api`：对外接口
- `config`：配置管理

产出物：

- 模块边界说明
- 目录结构建议
- 配置项草案

### 第 9 步：实现 MVP

第一版不要追求复杂，要先打通完整链路。

MVP 范围建议：

- 支持单一文档类型导入
- 支持基础切分
- 支持单向量库
- 支持 Top-K 检索
- 支持 rerank
- 支持问答接口
- 支持返回引用

不建议在 MVP 首版直接做：

- 多租户权限体系
- 复杂工作流编排
- 多模态 RAG
- Agent 化复杂调用链

产出物：

- MVP 可运行版本
- 基线测试结果

### 第 10 步：迭代优化与部署

在 MVP 跑通后再做效果和工程化优化。

优化方向：

- 查询改写
- 混合检索
- 更优 reranker
- 元数据过滤
- 缓存
- 文档增量更新
- 监控与日志
- 权限控制
- 反馈闭环

## 4. 推荐技术路线

以下是适合首版落地的建议，不代表最终定案。

### 4.1 语言与框架

- 后端语言：Python
- Web 框架：FastAPI
- 编排层：优先原生模块化，必要时再引入 LangChain 或 LlamaIndex

建议原因：

- Python 在 RAG 生态最成熟
- FastAPI 易于暴露问答接口和管理接口
- 首版不建议过度依赖重框架，避免链路不透明

### 4.2 向量库

首版建议优先级：

1. `FAISS`：适合快速验证
2. `pgvector`：适合与业务数据库整合
3. `Milvus`：适合中大型工程化场景

### 4.3 检索策略

默认路线：

- 语义检索
- 关键词检索
- rerank 重排

这比单纯向量检索更稳，特别是中文术语、产品名、制度编号、接口名场景。

### 4.4 大模型接入

模型层建议解耦，保留统一接口，便于替换：

- Embedding 模型接口
- Rerank 模型接口
- Chat 模型接口

## 6. 你需要审核并拍板的关键决策

在进入设计前，建议你确认以下事项：

1. 业务场景是什么
2. 首批接入哪类知识库
3. 是否只做中文
4. 是否要求返回引用来源
5. 是否需要多轮对话
6. 首版目标是本地验证还是可部署服务
7. 优先考虑效果、速度还是成本
8. 首版是否接受 `FAISS + FastAPI + Python` 的轻量方案

## 7. 审核通过后的下一阶段

如果你确认继续，我建议按下面顺序推进：

1. 输出详细系统设计文档
2. 初始化仓库结构
3. 实现文档导入与切分
4. 实现向量化与索引
5. 实现检索与重排
6. 实现问答接口
7. 加入评测与测试
